# incident-console-v2 Reference

Pages, routes, behaviour and configuration of `incident-console-v2`, the reviewer console of `dev-profile-incident`, and the analysis stages of agent mode as the pages show them. This is the reference companion of [`architecture.md`](architecture.md), which holds the containers, runtime views, deployment view and decisions; the console's code layout and import rules are in [`mvp2/console-hexagonal-architecture.md`](mvp2/console-hexagonal-architecture.md), the agent's HTTP contracts in [`vm-api-contracts.md`](vm-api-contracts.md), and the tables and object keys the routes write in [`data.md`](data.md).

## Console middle layer (ports and adapters)

`incident-console-v2` reaches Supabase, R2, the gateway and the agent through ports and adapters; the layout and dependency rules are in [`mvp2/console-hexagonal-architecture.md`](mvp2/console-hexagonal-architecture.md).

- A report is read from one `report_revisions` row (`?revision=<id>`, else the official one, else the newest). A refusal by a database write function becomes a `StoreRejection`, which the route returns as 422 with the database's reason.
- `/library` Find evidence posts to `POST /api/search`, which calls the agent's incident search ([`vm-api-contracts.md`](vm-api-contracts.md#post-apiv1incidentssearch)) with `{query, videoId?}`. Scoped to a video it returns 50 hits and the query may be empty, which lists that incident's evidence in video time order; without a video it returns 20 hits across the library. The VLM critic is off by default (`INCIDENT_SEARCH_CRITIC`), so no hit carries a verdict in the console. The Find incidents text search calls `POST /api/v1/incidents/revisions/search`, then filters the result in the console. A hit's report link carries `?t=` and the report page seeks to that second.

## Console configuration

Server-only variables, read from `incident-console-v2/.env.local` (a symlink to the profile's shared `.env.local`); none may be exposed through `NEXT_PUBLIC_`:

| Variable | Use |
|---|---|
| `ANALYSIS_MODE` | `gateway` (default) or `agent` |
| `VLM_GATEWAY_URL` | the gateway, required in gateway mode; `start.sh` exports `http://127.0.0.1:8600` in mock mode only |
| `INCIDENT_AGENT_BASE_URL` | the agent or the mock (chat, search, embeddings, and analysis in agent mode); uploads do not use it |
| `VLM_MODEL` | default model in the picker, one of `contracts/inference.json` (default `nvidia/nemotron-3-nano-omni-30b-a3b-reasoning`, Nemotron 3 Nano Omni Reasoning) |
| `CONTRACTS_DIR` | the shared `contracts/` directory (default `../contracts`) |
| `INCIDENT_SUPABASE_URL`, `INCIDENT_SUPABASE_SERVICE_ROLE_KEY` | PostgREST |
| `R2_ACCOUNT_ID`, `R2_ACCESS_KEY`, `R2_SECRET_KEY`, `R2_BUCKET` | video and evidence storage |
| `FFMPEG_PATH`, `FFPROBE_PATH` | override the npm-bundled `ffmpeg` / `ffprobe`; unset uses the bundled copy, then PATH |
| `ANALYSIS_JOB_LOOP` | `off` keeps this console's [background analysis loop](#background-analysis-jobs) stopped (its queued jobs then wait for another console); unset runs it |

`GET /api/health` answers `status` (`ready` or `degraded`) and per-service booleans only; the `gateway` row is omitted (and not probed) in agent mode and reported only in gateway and mock modes.

## Console pages

- **Shared header:** the Analyze, Library and Dashboard navigation uses a compact header (12 px vertical padding on narrow screens, 16 px from `sm`) and a 36 px brand mark. The Analyze hero and Library content start close beneath it rather than reserving a large blank band.
- **`/` (upload):** the model picker, a drop zone that takes one file or several, and the **Analysis jobs** list. The browser uploads and converts each file (`/api/uploads/r2`), uploads a WebP thumbnail (the frame 25% into the clip, at most 640×360, captured from the chosen file; a failure never blocks analysis) to `thumbnails/<video-key>.webp`, then queues its analysis as a [background job](#background-analysis-jobs) (`POST /api/jobs`); the console's server analyses jobs one at a time, so closing the tab does not stop a queued file (a file whose bytes are still being sent is lost with the tab, and the page says so). One file on an empty page shows the stored-name warning, a preview, the four stages (**Uploading videos**, which covers the upload and the H.264 conversion, then understanding, saving and report ready), and a redirect to its report when its job is done (or the job's failure reason, with **Retry analysis** retrying the job without re-sending the file). Several files, or any file added while a batch is on screen, form a **batch**: a row per file shows Queued, then Uploading (with percent, then elapsed time while the file converts; one **Uploading videos** step), then Queued again while its job waits, Analysing (elapsed time from the job's start, so a reopened page shows the real time), Done with an **Open report** link, Failed with the step and the reason, or Cancelled. Uploads run strictly one at a time, in the order added; a file waiting for or in analysis does not hold the next upload back. A failure never stops the next file. **Retry** on a failed row re-sends a file whose upload or conversion failed, or queues a failed job again; **Cancel** on a row whose job is queued cancels that job. A queued file can be removed; **Cancel batch** cancels every file not uploaded yet, aborts the running one only while its bytes upload, and cancels the batch's queued jobs (one already analysing finishes). The model is fixed per file when it is queued. The page reads `GET /api/jobs` every 3 s; the Analysis jobs list shows only the running and queued jobs (a finished job leaves it; its report is in the library), except those already shown as this page's own rows, so a reopened tab shows the same jobs and their progress. The queue is pure functions in `src/sections/analysis/batch-upload.ts`**A repeat is blocked:** a file whose content (SHA-256 as uploaded) is already a video, or is queued or running, is refused before it is stored: a single file shows "This video is already in the library as <name>" with **Open the existing report**, a batch row shows **Already uploaded** with the same link (no Retry), and nothing is uploaded or queued ([decision](decisions.md#2026-11-06-a-repeat-upload-is-blocked-by-file-content-and-the-reviewer-is-sent-to-the-existing-report)). A job still queued has no report yet, so the message names it without a link. The queue is pure functions in `src/sections/analysis/batch-upload.ts` ([decision](decisions.md#2026-10-31-batch-upload-runs-files-strictly-one-at-a-time-each-as-a-single-upload)).
- **`/library`** (the old `/reports` redirects here with its query string): Find incidents shows six cards per page, one per video (official revision, else newest). A card shows the incident type, its official status ("Official vN" or "No official version"), the title and a one-line summary under the upload-time thumbnail (`thumbnails/<video key>.webp`) with the severity and AI/Human badges on it, and a skeleton when the thumbnail is missing or fails to load; the file name and added date are in the title's tooltip, and the evidence and version counts are in the card's "..." menu; filters are text, type, report status (any, has an official version, not yet official), severity band, added date and sort, shown as chips and kept in the URL. The text search runs two matches on every query: the agent's meaning match (revisions scoring 0.25 or better, `REVISION_MIN_SIMILARITY`) and the library's plain word match (ILIKE over the type, title, description, file name and evidence text). The cards are listed in this order, paged in that order: found by both (best meaning score first), then word-only matches (in the order the sort gives), then meaning-only matches (best score first); the sort control does not apply while text is searched (a note says so). When the agent fails the word matches alone are listed, with a note. Find evidence shows the agent's top 20 hits with crop, match percentage, time, kind, threat and holder (no verdict badge: the critic is off); kind, threat and type filters and "Group by incident" work on the returned hits. A hit card shows the whole frame with its box and opens the report at the box second (`?t=`); there is no pop-up viewer. Find evidence has a Video filter and one Sort (best match, date, threat, severity), both applied in the browser. "See evidence" on a card scopes Find evidence to that incident and loads its evidence at once; a query typed while scoped searches only that incident (the agent filters by `video_id` in the database, not in the browser).
- **`/reports/<videoId>`:** On desktop the report fills the available viewport without document-level scrolling. A resizable, stationary left pane stacks the video, timeline and version graph; both separators inside that stack and the separator beside the report are keyboard-accessible. The right pane is the page's vertical report scroller, with report fields and one horizontal evidence-card carousel; raw run and model-output details are not displayed, and its View/Edit action bar stays anchored at the bottom outside that scroller. The existing video tracking overlay, picture-in-picture control and evidence detail pop-up remain available. Each evidence card shows its canonical id and title; clicking it opens the whole frame and box, description, holder/threat or held items, time and Play from here control. On smaller screens the video appears above the report. Edit mode is described below.
- **`/reports/<videoId>/compare?left=&right=`:** two AI revisions of one video side by side (`RunComparison`), opened from the report page when the video has another AI revision.
- **`/dashboard`:** see [Dashboard analytics](#dashboard-analytics-and-cross-filtering). The browser uploads a WebP thumbnail (the frame 25% into each new upload, at most 640×360, captured from the chosen file, which has the same frames as the stored copy) to `thumbnails/<video-key>.webp` under the stored `.mp4` key; a failure never blocks analysis.

## Background analysis jobs

An upload's analysis runs as a row in `analysis_jobs` ([`data.md`](data.md#analysis_jobs)), not inside the browser's request, so it survives a closed tab ([decision](decisions.md#2026-10-31-background-analysis-jobs-a-supabase-table-and-one-in-process-loop-per-console)).

- **Routes:** `POST /api/jobs {filepath, filename, model?, contentSha256?}` (a hash already held by a video or an active job is 409 `{error, duplicate}`; a malformed one is 400) checks the model against the allowlist (400 for an unsupported one) and queues a job with the model stored (the default model when none is sent) -> 201 `{job}`; `GET /api/jobs` -> `{jobs}`: every running and queued job, then the latest 10 finished; `POST /api/jobs/<id>/retry` (failed or cancelled -> queued) and `POST /api/jobs/<id>/cancel` (queued -> cancelled) -> `{job}`, or 422 for a job in any other state. Code: `src/modules/jobs/` (domain rules in `domain/job.ts`, use cases in `application/`, PostgREST adapter in `infrastructure/supabase/`). `POST /api/analysis` runs one analysis inside its request, for scripts and tools; the upload page does not call it.
- **The loop:** `src/instrumentation.ts` starts `src/lib/jobs/loop.ts` once per console process (Node.js runtime only; a `globalThis` flag stops the dev server starting a second one, and the atomic claim makes a second loop harmless anyway). Every 3 s it calls `claim_analysis_job(p_stale_seconds)`, which takes the oldest queued job (`FOR UPDATE SKIP LOCKED`), then runs `analyseUpload` (`src/modules/analysis/application/analyse-upload.ts`), the same code `POST /api/analysis` runs, heartbeats the job every 15 s (`touch_analysis_job`), and stores done with the new video and AI revision, or failed with the plain reason (`finish_analysis_job`). It takes the next job at once when one finished. One job at a time per console keeps it in line with the batch upload and the hosted endpoint's rate limits. The loop is not a request, so the route's 660 s `maxDuration` does not bind it. In agent mode an analysis is limited to 600 s (`INCIDENT_ANALYSIS_TIMEOUT_SECONDS`, default 600; from 7 Nov 2026, was the model's 300 s); gateway mode keeps each model's `timeout_seconds` in `contracts/inference.json`. The agent call uses `node:http`, because Node's fetch gives up on a response with no headers after 300 s (`UND_ERR_HEADERS_TIMEOUT`) and the agent sends nothing until it has saved. The heartbeat (15 s) runs on its own timer, so a 10 minute run is never stale (stale is 180 s without a heartbeat). A run still waiting on the agent's main call at 600 s fails with "The analysis did not finish within 600 s: the model's main call was still running, so no report was saved".
- **One video per job:** every attempt of a job analyses into the same video id, derived from the job (`jobVideoId`), so a run cut short and run again, or a retry, adds revisions to one video instead of leaving a second video row on the same R2 object.
- **Recovery:** a running job with no heartbeat for 180 s lost its console (stopped or restarted). The next claim, by any console, sends it back to the queue after its first stale run and fails it ("The console stopped twice while analysing this video") after the second, so nothing hangs. A heartbeat or finish names its claim (`p_attempt`), so a runner whose job was recovered cannot overwrite the newer claim.
- **Shared queue:** every console pointed at finals with the loop on claims from the same table, and a job runs against the agent or gateway of whichever console claims it. Set `ANALYSIS_JOB_LOOP=off` on a console that must not take other people's jobs.

## Report library pagination and deferred report loading

```mermaid
sequenceDiagram
    actor User as Reviewer
    participant UI as /library
    participant API as Next.js /api/reports
    participant DB as Supabase RPC
    participant R2 as Cloudflare R2

    User->>UI: Open library or change metadata/evidence filter
    UI->>API: GET summaries (page size 6; entity/instrument/asset terms)
    API->>DB: list_incident_report_summaries(...) (IncidentRepository.listReports)
    DB-->>API: 6 summaries + total count
    API->>R2: Sign up to 6 derived thumbnail keys
    API-->>UI: Metadata + small thumbnail URLs (no video URL)
    UI-->>User: Lazy screenshot images or skeleton fallback
    User->>UI: Open one report
    UI->>API: GET /api/reports/videoId?revision=revisionId
    API->>DB: Read one report_revisions row (IncidentRepository.getReport)
    API->>R2: Create selected object's signed URL
    API-->>UI: Full report + playback URL
```

Date inputs are directly editable: entering either boundary activates the custom range automatically. Preset
selection clears stale custom boundaries, and the date/time row has an explicit reset that clears both date and
time constraints. The API forwards inclusive day boundaries, optional time-of-day bounds, and the viewer's detected timezone to the summary RPC.

## Dashboard analytics and cross-filtering

`GET /api/dashboard` calls the service-role-only `get_incident_dashboard` RPC through `DashboardRepository.getDashboard`. It counts **one report per video: the official revision, else the newest**, the Library's rule, and reports how many are official and how many are not yet official. Nothing is marked official by being counted.
- The page shows eight fixed displays: Total reports (the official and not-yet-official split, and a neutral **N revised** chip beside the big total: the counted reports whose video has more than one version, shown with a history icon, a tooltip that explains "N of these reports have 2+ versions (edited or re-analysed)" ("1 of these reports has 2+ versions (edited or re-analysed)" when N is 1) on hover and keyboard focus, and that full text as its accessible label; not a split part, no official or not-yet-official colour, not linked because the Library has no version filter, and hidden when the count is 0), with Activity by day and hour beside it in the wide slot (a heatmap of report time in the viewer's zone; select a cell to filter the page; All, Official and Not yet official toggle), then Incidents by type and Top targeted assets (ranked bars), Severity breakdown (a donut with the split listed beside it; the list is the filter control), Evidence by kind (the counted reports' entities, instruments and assets, split), Top instruments and Entity types (ranked split bars, unlinked). The trend chart (Reports generated over time) is removed from the page; the RPC still returns its daily `trend` and Ask for a chart still charts it. A field the RPC does not return (a definition older than `20261106140000`: `multipleVersions`, `evidence`, the entity and instrument split) is read as not loaded, never as 0: the revised chip is omitted, Evidence by kind says it is not available yet, and Top instruments and Entity types draw their totals alone. Every display with a split shows it ([decision](decisions.md#2026-11-06-dashboard-calendar-range-several-versions-line-and-evidence-displays-the-trend-is-titled-by-report-time), amended for the stat by [2026-11-06 header and stat](decisions.md#2026-11-06-dashboard-drops-the-previous-period-comparison-adds-an-ask-for-a-chart-jump-and-restyles-the-several-versions-stat), amending [2026-11-01](decisions.md#2026-11-01-dashboard-displays-take-the-form-their-data-suits)). The RPC still returns the other sections (threat levels, confidence, model coverage) for the port's other callers.
- `DashboardQuery.scope` (`all`, `official`, `not_official`; `GET /api/dashboard?scope=`) narrows the statistics to one report status. The route defaults to `all` and always sends it to the RPC.
- All-time video counts are shown as a static note on the Total card.
- Evidence statistics are normalised asset names (and canonical entity types and instrument names in the RPC), counted per distinct incident.
- The total, its official and not-yet-official counts, and the type and asset rows link to `/library?scope=all|official|not_official&...` with the same period and filters, using `match=exact` for asset names, so the Library total equals the clicked number. The URL is the reports page's filter state. Severity rows and heatmap cells filter the page instead.
- Before the first load the panels show skeletons, and a failed first load shows an error with Try again: the page never shows a 0 it has not loaded. A failed refresh keeps the last figures under an error.
- The period window is computed in the browser after mount and sent as zoneless UTC; the API reads it as UTC.
- The period is a preset (last 7 or 30 days, all time) or **Choose dates**: a calendar range (shadcn `Calendar` in a `Popover`, range mode; days after today are disabled; Apply commits, Cancel keeps the period). Choosing **Custom range** in the period select opens the same calendar, and choosing it again while a range is applied reopens it with that range. The browser sends the range as zoneless UTC from local midnight of the first day to local midnight after the last (`customWindow` in `domain/charts.ts`), with `days=custom`; `GET /api/dashboard` requires both `after` and `before` for `custom`. Every display and every Library drill-down link uses the same window, so the totals match.
- **Header and jump:** the header has no comparison with the previous period (the RPC still returns `previous` for a bounded period, and the console does not read it). Its **Ask for a chart** button scrolls smoothly to the section at the foot of the page (`id="ask-for-a-chart"`) and focuses its request box (`id="chart-request-text"`), both ids exported from `src/sections/dashboard/chart-request-jump.ts`; with `prefers-reduced-motion` the scroll is instant.
- **Ask for a chart:** `POST /api/dashboard/chart {request, chartType, timezone}` takes one request and the user's chart kind (bar, stacked bar, horizontal bar, donut, line or area; `pie` is read as donut), and answers `{kind: 'chart', chart}`, `{kind: 'unsupported'}` or `{kind: 'needs_bar'}`. The model only picks a strict `ChartSpec` from the allowlist in `modules/dashboard/domain/chart-spec.ts`. Its `period` is a preset or a calendar period: `{month}` (`YYYY-MM`), `{day}` (`YYYY-MM-DD`) or `{from, to}`, which must be real dates, not after today in the viewer's time zone, not reversed and at most 366 days (`domain/chart-period.ts`; a month still running counts up to today). The console sends the model today's date and the viewer's zone in the user message, so "October" resolves to the most recent one not in the future. `generateChart` counts a calendar period from local midnight of its first day to local midnight after its last, titles the chart with the range in words (for example "Reports per day, 1 to 15 October 2026") and passes the same range to `getDashboard`; `generateChart` runs `getDashboard` (plus one query per report status for report charts), builds the rows, title and labels itself, and sends the figures and the palette colours to VSS `chart_generator` on the agent through the `ChartRenderer` port. The agent returns a Chart.js configuration with those figures in it; the console checks every label and figure against its rows (`domain/chart-config.ts`) and answers a 502 on a mismatch, so no altered figure is shown. The browser draws the configuration with `chart.js` and `react-chartjs-2` (`ChartJsView`, loaded only when a chart comes back); the Table tab gives every row and the chart's accessible label names its title, scope and totals. With no configuration back (a `200` with `chart_config: null`, or the agent answers `422`, `404` or `501` for the Chart.js item, as an agent without Chart.js output does), the PNG is drawn instead (a donut as a pie, the rest as bars); any other failure is a 502. A kind that does not suit the dimension answers `needs_bar`: a stacked bar needs the official split, a donut needs a whole, a line or area needs a day, week or month trend, and a bar always suits (`domain/chart-kinds.ts`). Colours are in `src/lib/ui/chart-colors.ts`; no records means nothing is drawn. Before the model reads the request, `generateChart` normalises canonical severity words to their dashboard band in code (`domain/severity-words.ts`, `chart-severity-words-v2`: a word maps only when all the severity levels the project definitions tie it to share one band: minimal, very low and minor→low, moderate→medium, severe and critical→high; only where the word qualifies severity or an incident noun; serious, significant and other words stay as typed; [decision](decisions.md#2026-11-03-dashboard-chart-requests-normalise-canonical-severity-words-in-code)). The console posts its prompt and the (normalised) request to the agent's `POST /api/v1/incidents/chart-requests`, where the agent's own LLM (`chart_generator.llm_name`) answers with the JSON object it wrote; the console validates that object as above. Invalid input is 400, a missing `INCIDENT_AGENT_BASE_URL` 503, and a failed model or drawing call a plain 502 ([decision](decisions.md#2026-11-02-dashboard-chart-requests-are-read-by-the-vss-agents-own-llm-not-the-local-vlm-gateway), amending [2026-10-31](decisions.md#2026-10-31-dashboard-chart-requests-a-model-picks-an-allowlisted-spec-our-code-fetches-the-figures-and-vss-chart_generator-draws-them); calendar periods: [decision](decisions.md#2026-11-06-dashboard-chart-requests-take-calendar-periods-a-month-a-day-or-a-range-read-against-today-in-the-viewers-time-zone)).
- The heatmap and its weekday/hour cross-filters use the viewer's local time: `GET /api/dashboard` forwards the browser's detected `timezone` (e.g. `America/New_York`) to `p_timezone`, which groups and filters `generated_datetime` in that zone. `/library` detects the same zone itself, so drill-down links carry no timezone and the totals still match. The old `/reports` URL redirects to `/library` with its query string.

## Report versions: View, Edit and History

After **Analyse this box**, the evidence review opens on the frame the reviewer selected and reuses the browser-loaded video. It does not swap to a secondary still-frame request that can fail and leave a black preview. **Add to draft** is not blocked by an ffmpeg crop request: the new evidence card previews the selected timestamp and box from the browser-loaded video, while the final Save creates and stores the authoritative reviewer evidence image.

When final Save stores reviewer-added evidence, it extracts the crop and full frame sequentially. This avoids running two memory-heavy ffmpeg processes for one item and prevents signal-terminated `exit code null` failures.

If the bundled ffmpeg segfaults while reading a signed R2 URL, frame extraction streams that video to a temporary local file, retries from disk, and removes the temporary file. Other ffmpeg failures are returned without retry.

The Ask sheet is flush with the browser edge, keeps its Close control at the top-right, and labels the selected version without an “Asking about” prefix.

Edit-mode evidence pairs use compact carousel slots sized to the evidence cards rather than stretching across the report pane. Each saved A card and editable B card occupies its own aligned swimlane in the same evidence column; sticky A/B markers on the left remain visible while the lanes scroll horizontally and share a neutral color treatment. Dotted vertical separators divide evidence columns, with no extra wrapper boxes around the cards. View and Edit cards share a 22rem maximum width, a full-frame 16:9 video thumbnail flush to the top and bottom card edges, and a tinted title band; Edit's name input has a visible outline in that band to show it is editable, with the remaining editable fields below it, while View retains its full evidence details. In both modes, the previous/next controls sit below **Add evidence**.

The read-only A evidence card in Edit mode mirrors View mode’s badges: its canonical `E1`/`I1`/`A1` ID sits beside the title and its Entity/Instrument/Asset badge overlays the image. There is no additional type badge outside the paired cards, and the editable B card does not add these badges.

The Edit track dialog uses the same full-width neutral title band as Re-analyse. It shows the evidence identity on one line (`E1 · Man in blue shirt`), followed by separate type/source metadata and two-step editing guidance.

The report page has two modes. **View** shows the version on screen as **Now Viewing: Version N**, with all report fields grouped in one **Report fields** section, plus its version graph, official star and evidence cards. In the version graph there is no View button: a click anywhere on another version's row (or Enter on its focused row) opens it, and the official star only toggles official. In Edit mode the report title is an input in the draft column, like the other report fields: a change counts as an unsaved change, Undo and Revert restore it, a blank title stops Save, and Save stores it on the new human version's `payload.incident.title`. In View, a title a reviewer changed reads "Set by a reviewer. The model's title: ...". A human version's row shows the first 10 characters of its note and an ellipsis when cut (the row's hover title has the whole note, and the stored note is unchanged); an AI row shows its whole model name. The version summary, report fields and evidence sections use tinted title bands with an accent border; each evidence card also separates its title from its details with a tinted header. The Timeline and Versions panels keep the prominent accent treatment. The **Re-analyse incident** modal and **Ask about this incident** sheet instead use clean neutral title bands with larger bold titles and no left accent line; chat's New chat and Close controls share the title's aligned header row. The chat suggestion list contains only **Show the timeline of events**. The two top-bar action buttons share a subtle primary tint. The timeline is labelled **one lane per entity and what they hold** and its legend reads **Entities**, **Instruments** and **Assets**. The report page does not link to the separate analysis-run history screen and does not display raw run or model-output details. When no revision is official, View and Edit show **No official version has been selected for this video. Star a version to make it official.** once inside their version-summary card. The View evidence section has a thin header (title, count and description on one row, with the carousel arrows at its right) above a horizontal carousel; it has no **Add evidence** button, which only Edit mode offers. **Edit from vN** opens **Edit** mode, where the version being edited is shown as read-only A alongside editable B. Edit uses the same card-based section headers as View for its version summary, report fields and evidence; the A/B values stay visually distinguished, and evidence pairs are arranged in a horizontal carousel with sticky A/B lane markers. In Edit mode, carousel arrows sit below **Add evidence**. View and Edit cards share a 22rem maximum width, a full-frame 16:9 video thumbnail flush to the top and bottom card edges, and a tinted title band; Edit keeps its name input in that band and the remaining editable fields below it, while View retains its full evidence details. Evidence cards retain **Edit track** for keyframe changes; the per-card **Edit** action for changing the evidence box or image is removed. Edit mode identifies its base as **Now Editing: Version N**; it provides **Go back to view** beside **Save as new version**, preserving the unsaved draft when switching back. That history row says **Editing**, while every other revision offers **Edit**. Choosing another revision discards the unsaved draft and starts a fresh draft from that version. Deleting an entity deletes the instruments it holds; a pair's Revert restores that item as in A. Draft-level **Undo** walks backward through changes and **Revert all** restores the opened version; neither writes a revision.

**Person tracks.** When an entity's evidence entry carries a track (agent mode with `INCIDENT_TRACKING_ENABLED=1`, a person matched to a track), View mode draws a box that follows that person over the report video (`TrackOverlay`): one stable colour per tracked item from a pool of ten shared by entities, instruments and assets (assigned in entity, instrument, asset then id order, so a report's first ten tracked items never share one; the same colour draws the box, its label, the card ring and the presence bar for the whole clip), labelled with its name (never its id: `E1`, `T-1`), the box at the playhead interpolated between samples up to 1 s apart, held for 0.5 s at the span ends and hidden outside them or inside a longer gap. It is drawn with `containFrame` so it stays on the picture, takes no pointer events (the player's controls work through it), follows the playhead every frame while playing, and is hidden while the video is in picture-in-picture. In Edit mode the overlay draws the draft instead of the opened version (`draftOverlay`), so a change shows before Save: an unchanged item keeps its saved track or still box (found through its source id), a re-tracked or added item shows the reviewer's samples or still held in the browser, a Set image pick moves an untracked item's box, a deleted item's box goes at once and Undo brings it back, and the box of the item whose **Edit track** dialog is open is hidden until Done. Draft colours follow the order Save stores (a new item joins the end of its kind), so they match the saved version; a new tracked item shifts only the tracked items of later kinds. The Timeline panel draws the same draft in Edit mode (`draftToStructured`, with the frames from `draftOverlay`): names, spans, holder lanes, added and deleted items update as the draft changes and Undo restores them, and an entity whose evidence image Save will cut anew (a pick, a track's first sample or a reviewer still) shows that frame and box as its thumbnail. "Go back to view" and leaving without saving return the panel to the saved version. Each tracked card shows a presence bar (`PresenceBar`): the track's span over the whole clip in the item's colour; a click on the span seeks to that second, anywhere else on the bar (or a key press) to the span's start. An item with no track shows its stored box on the player instead, dashed amber (`stillBoxFor`), from 0.25 s before `box_seconds` to 2 s after it, playing, paused or scrubbing (`stillBoxShows`); overlapping boxes are all drawn. Its pop-up's Play from here seeks to `box_seconds`, pauses and selects that box; the card then reads "Not tracked: <reason>" when the agent recorded `track_gap`. A person whose box came from the track that fits the report's seconds (the evidence entry's `box_source: "track-time"`, no detector found them) carries a **Matched by time** badge on the card and in the pop-up. A click on a card with a track or a stored box selects its box (thicker; the others dimmed); a click on the selected card's text clears it, and a new version starts unselected. The detail pop-up shows "On screen x-y (tracked)" beside the report's own on-screen span (contract v4: `first_seen`/`last_seen` are never rewritten) and the bar, whose click closes the pop-up and seeks. The browser reads the samples from `GET /api/reports/[videoId]/track?revision=&type=&item=` (`getEvidenceTrack`), which takes the key from the stored revision's evidence entry, reads the JSON from R2 on the server (R2 has no CORS rule for the console) and answers `{samples: [{t, box}]}`: 404 without a track, 502 when the file cannot be read, and an empty list for a malformed file; the overlay reads each track once per page load and draws nothing for one that fails. - **What a reviewer may edit:** the structured (Class A) fields and each item's image; model output and provenance are read-only ([field classes](analysis-schema.md#three-classes-of-report-fields)). `PATCH /api/reports/[videoId]/edit {parentId, editedBy, edit, note?}` rejects Class B/C keys (400), validates the edit against the contract's own sub-schemas and ID/holder/window rules (422), builds the new payload and evidence (`humanRevisionContent`) and calls `save_human_revision_with_crops`, which appends a `human` revision whose parent is the revision that was opened. On a video with no official revision the route first asks the agent to embed the new evidence and the same call stores the crops; an embedding failure answers 502 and saves nothing ([`data.md`](data.md#save_human_revision_with_crops)). `GET /api/reports/[videoId]/revisions` is the History list. `POST /api/reports/[videoId]/evidence-image` stores an image under a new R2 key and returns the key for the edit to use (Save cuts a reviewer item's image on the server, from the box tool's track or from `image_pick`, so the console reaches this route only for a pending image, which nothing sets today). No route changes a revision, `model_runs.notes` or an existing R2 object, and there is no verify step.

The report shows "Model assessed N/5; reviewer set M/5" beside the model severity rationale, and the model's original window beside a reviewer-set one.

- **Upload (API):** `POST /api/uploads/r2` (multipart `file`, `filename`) first hashes the file (SHA-256, streamed) and answers 409 `{error, duplicate}` when a video or an active job already has that content, storing nothing; otherwise it writes the file to a temporary directory, probes it with `ffprobe` and stores it in R2 as `uploads/<name>.mp4`: an ISO MP4 whose video is already 8-bit yuv420p H.264 is stored byte for byte (`converted: false`); anything else (phone HEVC `.MOV`, 10-bit H.264, MKV, WebM) is converted with `ffmpeg -map 0:v:0 -an -c:v libx264 -preset veryfast -crf 20 -pix_fmt yuv420p -movflags +faststart` into a temporary MP4 at the same width, height and frame rate, with no audio, which is streamed to R2 and deleted (`converted: true`); the answer carries `contentSha256`, the hash of the file as sent, which the page passes to `POST /api/jobs`. The temporary files are removed on every path, success or failure. The stored name always ends in `.mp4` (`inspectUploadName`), so `POST /api/uploads/check` reports `clip.MOV` as `clip.mp4`. A file `ffprobe` or `ffmpeg` rejects is 422 with their last lines; a missing binary is 503; a file over 5 GB is 413; the route's `maxDuration` is 1800 s and the conversion may take 25 minutes (limits documented in the profile `.env`). The upload page keeps its **Uploading videos** step active once the bytes are up and shows the conversion's elapsed time there, then "Converted ... in m:ss" or "Already an H.264 MP4: stored without conversion". ([decision](decisions.md#2026-10-31-every-upload-is-stored-as-an-h264-mp4-at-the-original-resolution-converted-by-the-console-with-ffmpeg)).
- **Track editor (console only):** `TrackEditor` (dialog), `TrackFrame` and `TrackTimeline` edit an `EditorTrack` (start, stop, keyframes) from `modules/reports/domain/track-editor.ts`; `trackEditorSource` picks the starting track (the draft's reviewer track, else the saved AI track from its track route, else a still box). - **Frames and crops (API):** `GET /api/reports/[videoId]/frame?t=` returns one frame as a JPEG, and `POST /api/reports/[videoId]/evidence-crop {timestampSeconds, region}` cuts a rectangle (fractions 0-1 from the top-left) from that frame and returns it as a JPEG, writing nothing. A malformed `t` is 400, a `t` at or past the video's length or a region outside the frame or under 1% wide or high is 422, an unknown video is 404, and a missing `ffmpeg` is 503. The crop is cut on the server because R2 has no CORS rule for the console origin, so a browser canvas crop of the signed video would be tainted. Both use the console's `ffmpeg` (bundled by `npm install`; `FFMPEG_PATH`/`FFPROBE_PATH` override; PATH fallback). In Edit mode, **+ Add evidence** opens the box tool (`BoxTool`): pick a second, draw a box, **Analyse this box** (the describe route names it, the track route follows it), then check the AI-filled card beside the tracked preview (type, name, description, holder and threat for an instrument; scrub; **Extend 3 s** back or on; **Adjust box**; **Gone from here on**) and **Add to draft**. A lost track offers keep as incomplete, redraw or keep as still image; an AI miss leaves a blank card to fill in. ## Re-generation and the official version

- **Re-generation.** `POST /api/videos/[videoId]/runs {model, additionalInstruction?}` re-analyses the stored R2 object (the console's "reviewer prompt" box is `additionalInstruction`):
  - the same canonical request, strict validation and ID-only recovery as an upload;
  - always a new run and a new AI revision, which starts from the model's output (earlier edits are not carried across);
  - it never writes the `videos` row (the upload time is kept);
  - it never changes the official version.
- **Official version.** `PUT /api/videos/[videoId]/official {revisionId}` and `DELETE` call `setOfficialRevision`: for a mark, the console asks the agent for the revision's evidence embeddings (`POST /api/v1/incidents/evidence-embeddings`) and passes them to `set_official_revision`, which sets `videos.official_revision_id` and rebuilds the incident's `evidence_crops`; for a clear it passes none and the rows go. If the agent is unreachable the mark fails and nothing changes. Used from the report page.
- **Model choice:** both modes send the chosen allowlisted model (gateway to `vlm-gateway`, agent as `model` on `/analyze`). The run records the model the agent reports, so in agent mode the recorded model is the agent's.
- **Where it appears:** `ReanalysisDialog` in the report page's top bar. There is no `/videos` or `/videos/[id]` page and report-card menus do not expose analysis history. The runs route remains the re-analysis command endpoint.
